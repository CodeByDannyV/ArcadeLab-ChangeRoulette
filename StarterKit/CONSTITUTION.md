# Network Change Roulette (CR) · Constitution input

**Purpose.** Help networking learners trace a change from the visible source IP to the firewall rule and explain which caseworkers lose service.

**First playable milestone.** One complete round for an IPv4 allowlist change. The NAT and service-to-service proposals need their own reviewed fixtures before they enter the game.

1. **Technical truth.** Derive results from fixture data and a documented networking rule. Validate authored data before play. Check the model against independently worked examples.
2. **Learning through decisions.** Show the ticket, rules and source IPs before asking for a prediction. Explain each result with the matching rule or default deny. Provide a reasoning hint and a worked solution, and track both as assistance.
3. **Honest progress.** Count only valid submissions. Allow retries and require a correct answer to advance. Count a correct first submission without assistance separately. Confirm restart and reset on page reload.
4. **Keyboard and motion.** Use native controls, visible focus, useful focus transitions and text outcomes. Make replay and controls immediately usable in reduced motion and at narrow widths.
5. **Self-contained runtime.** Host ordinary static files. Use authored content and local calculations. Let the wheel vary reveal order while the firewall model determines every outcome.
6. **Separate content, rules and session state.** Make additional allowlist fixtures data changes. Keep replay explanations tied to the evaluator.
7. **Demonstrate completion.** Keep requirements, tasks and the README aligned. Record observed checks and remaining work.
